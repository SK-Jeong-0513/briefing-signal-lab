주간까지는 버티고, **09-29(화) 일일부터 실패**한다(필요 54 · 잔여 45).

### Workspace 이전(경로 B)은 기각됐다
2026-09-23 11:02 checkQuota 실측: `noreply@brevislab.com` **잔여 100**. 한도가 여전히 100이라
트리거를 옮겨도 얻는 것이 0이다. 공식 문서의 «누적 결제 100달러 + 60일» 쪽이 맞는 것으로 본다.

### ZeptoMail 도 기각됐다
ZeptoMail 은 **트랜잭션 전용**이고 뉴스레터·대량 발송을 명시적으로 금지한다. Zoho 공식 FAQ 가
«대량은 Zoho Campaigns 를 쓰라» 고 답한다. 계정 심사에서 막히거나 나중에 정지된다.
→ 2026-09-14 핸드오프의 «후보는 ZeptoMail» 은 잘못된 전제였다.

### 왜 Resend 인가
무료 3,000통/월 · 100통/일, 로고 강제 없음, API 가 가장 단순해 `sendMail_` 한 함수로 끝난다.
2026-09-14 검토에서 «일일 100통» 때문에 탈락시켰으나 **구독자 54명이면 일일 54통**이라 들어간다.
월요일은 일일이 생략되므로 하루 최대가 54+α 다. **구독자 약 90명에서 일일 100통에 닿는다** —
그때 Pro($20/월 · 50,000통)로 올린다.

## 2. 설계

### 전환 스위치는 코드가 아니라 스크립트 속성이다
`RESEND_API_KEY` 스크립트 속성이 **있으면 Resend, 없으면 기존 GmailApp** 으로 간다.

이유가 셋이다.
1. **CFG 를 건드리지 않는다.** 수동 배포는 52행~끝 교체가 원칙이고 CFG(20~51행)에는
   SALT·TEST_MODE·MARKET_SHEET_ID 가 있다(§6). 스위치를 CFG 에 두면 그 원칙이 깨진다.
2. **키를 코드에 넣지 않는다**(전역 §5 하드코딩 금지).
3. **되돌리기가 속성 삭제 한 번**이다. 코드 재배포가 필요 없다.

### ⚠️ 조용한 폴백을 만들지 않는다
Resend 발송이 실패해도 **GmailApp 으로 되돌아가지 않는다.** 예외를 그대로 올려 호출부의
`catch` 가 `failed++` 로 세게 한다. 조용히 Gmail 로 새면 하루 100통 한도에 걸려 절반만
나가는데, 일일은 수신자별 로그가 없어 그 상태가 복구 불가다(전역 §18).

### 한도 가드는 «수단» 과 짝을 맞춘다
`mailQuotaOk_` · `mailQuotaWarn_` 는 `MailApp.getRemainingDailyQuota()` 즉 **Gmail 한도**를 본다.
Resend 로 보내는데 이걸 보면 **엉뚱한 수치로 발송을 막는다** — 일일은 fail-closed 라
전환해 놓고도 계속 안 나간다.

→ Resend 경로에서는 두 가드를 통과시킨다(Gmail 잔여와 무관하므로).
→ Gmail 경로에서는 **지금 동작 그대로** 유지한다. 수단과 가드가 항상 짝이 맞는다.
→ 대신 **발송 건수를 로그에 남긴다**(전역 §18 — 건수가 없으면 결손이 안 보인다).

### From 과 reply_to
- `From`: `Briefing Signal Lab <noreply@brevislab.com>` (검증된 도메인이어야 한다)
- `reply_to`: `CFG.OPERATOR_EMAIL` — **반드시 넣는다.** 지금은 개인 Gmail 이 발신이라 구독자
  회신이 그대로 운영자에게 온다(2026-09-22 W39 회신 실례가 있다). reply_to 를 빠뜨리면
  회신이 noreply 로 가서 사라진다.

### 429 재시도
Resend 기본 한도는 **10 req/s** 이고 현재 발송 속도는 약 0.8/s(45통 56초)라 여유가 크다.
그래도 429 면 짧게 한 번 쉬었다 재시도한다 — 실패 비용이 «그 사람만 못 받음» 이라 싸지 않다.

### 이번 범위에서 뺀 것
- **`List-Unsubscribe` 헤더** — naver·Gmail 전달력에 도움이 되지만 수신자별 토큰이 필요해
  `sendMail_` 시그니처를 바꿔야 한다. 별건으로 남긴다.
- Resend **batch 엔드포인트**(100통 묶음) — 지금 루프가 수신자별 실패를 따로 세고 있어
  그 구조를 지킨다. 속도 문제가 없으므로 바꿀 이유가 없다.

## 3. 성공 기준

```
1. 도메인 인증          → Resend 콘솔 Verified            [완료 2026-09-23 12:08]
2. DNS 충돌 없음        → 루트 MX·SPF·google._domainkey·_dmarc 불변  [완료, 실측]
3. sendMail_ 이 Resend  → 운영자 주소 1통 수신 + Resend 로그 delivered
4. 가드가 수단과 짝     → 테스트가 잠금
5. 국내 도메인 도달     → naver·hanmail 각 1통 인박스(스팸함 아님)
6. 09-29(화) 일일       → Resend 로그 54건 delivered
```

## 4. 남은 위험

- **국내 포털 전달력.** 구독자 54명 중 naver 약 10 · hanmail 약 3 = **약 24%**. 지금은 Gmail 이
  직접 보내 문제가 없지만 서구 ESP 로 바꾸면 스팸함으로 갈 수 있다. 5번 기준이 이걸 막는 관문이다.
- **첫 회차 성공은 검증이 아니다**(전역 §18). 09-29 이후 최소 2회차를 더 본다.
- **주간 발송 사본이 개인 계정 Sent 에 30일간 0건**이다(휴지통 포함, 일일은 정상). 제목 특정
  Gmail 필터로 보인다. 한도와 무관한 별건이지만, **같은 형태로 `[BSL]` 운영자 알림도 14일간
  0건**이라 한도 부족·발송 실패 알림이 와도 안 보일 수 있다. 전환과 별개로 확인이 필요하다.

## 6. 배포 순서 (⚠️ 붙여넣기 = 전환이 되지 않도록)

`RESEND_API_KEY` 가 이미 설정돼 있으므로 **코드를 붙이는 순간 다음 트리거부터 Resend 로 나간다.**
성공한 발송이 한 번도 없는 상태에서 54명 일일이 첫 시도가 되면, 실패 시 전원이 못 받고
일일은 수신자별 로그가 없어 복구가 안 된다. 배포와 전환을 분리한다.

```
1. 스크립트 속성에서 RESEND_API_KEY 를 «삭제»            → 전환 스위치를 내린다
2. 52행~끝 교체 후 저장                                   → 동작은 오늘과 동일(Gmail 경로). 무해한 배포
3. RESEND_TEST_TO 에 naver·hanmail 주소를 넣고
   RESEND_API_KEY 를 «다시 추가» → checkResend() 실행     → 실제 HTML 본문으로 1통씩
4. 두 곳 모두 «인박스» 인지 눈으로 확인 (스팸함이면 중단)
5. 통과하면 키를 그대로 두고 트리거에 맡긴다
```

되돌리기는 **속성 삭제 한 번**이다. 재배포가 필요 없다 — 그러려고 스위치를 속성에 뒀다.

단락하기 때문이며 이는 설계대로다. 첫 회차 뒤에는 **메일함이 아니라 Apps Script 실행 기록**을

## 7. 전환 후 달라지는 운영 사실

**Gmail Sent 에 BSL 발송 사본이 더는 남지 않는다.** 2026-09-23 오전에 구독자 수를 실측할 때
`in:sent subject:"일일 시황"` 으로 개별 발송을 세어 45통을 확정했는데, **그 방법은 이제 못 쓴다**
(발송이 Gmail 을 거치지 않는다). 앞으로 발송 건수의 근거는 둘이다.
  - Resend 대시보드 → Emails (수신자별 delivered / bounced)
  - Apps Script 실행 기록의 `[일일 …] 발송 N · 건너뜀 · 실패` 와 `[한도] … 대상 N명`

**실패해도 운영자 알림 메일이 오지 않는다.** 한도 가드가 `sendMail_` 통지 앞에서 단락하므로
설계대로다. 게다가 `[BSL]` 알림은 2026-09-23 기준 14일간 0건이라 Gmail 필터에 걸려 있을
가능성이 있다(§4). **첫 회차 뒤에는 메일함이 아니라 실행 기록을 본다.**

## 8. 남은 검증 (첫 회차 성공은 검증이 아니다 — 전역 §18)

| 시점 | 대상 | 확인 방법 |
|---|---|---|
| 2026-09-28(월) 09:00 | 주간 브리핑 W40 | 실행 기록 `[주간 …] 발송 N`, Resend Emails N건 delivered |
| 2026-09-29(화) 07:2x | 일일 시황 (첫 대량 일일) | 같은 방식. **여기가 원래 한도로 깨지던 회차다** |
| 2026-09-30(수) 이후 | 2회차 이상 | 형식·수량이 흔들리지 않는지 |

추가 감시 항목
- **Resend 무료 한도는 일일 100통 · 월 3,000통**이다. 구독자 54명 기준 월 약 1,200~1,650통이라
  여유가 있으나, **구독자 약 90명에서 일일 100통에 닿는다**(월요일은 주간만 나가므로 하루 최대가
  구독자 수 + α). 그때 Pro($20/월 · 50,000통)로 올린다. 2026-09-23 하루에만 9명이 늘었다.
- 반송(bounce)·스팸 신고가 쌓이면 Resend 가 발송을 막는다. Emails 탭에서 주기적으로 본다.

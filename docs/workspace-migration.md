# Google Workspace 이전 — 발송 한도 해제

> 작성 2026-09-01. 착수 전 이 문서를 끝까지 읽고, **§3 조용히 깨지는 것**을 먼저 이해할 것.
> 이 이전의 위험은 "안 되는 것"이 아니라 **"되는 것처럼 보이는데 조용히 깨지는 것"**이다.

## 1. 왜 하는가

2026-09-01 화요일 일일 시황이 발송되지 못했다(필요 35 · 잔여 29). 구독자 35명이 그날 메일을 못 받았고 **복구되지 않았다** — 일일은 수신자별 발송로그가 없어 이어서 보낼 수 없다.

원인은 한도 계산 방식이다.

```
Gmail 발송 한도는 달력 하루가 아니라 롤링 24시간이다.
  월 07:20  일일 35
  월 09:06  주간 35     ← 화요일 아침 창에 그대로 남는다
  ─────────────────
            71 소진 → 화 07:20 에 29 남음 → 35 필요 → 보류
```

**일일이 매일 나가므로 창에는 항상 2일치가 겹쳐 있다.** 여기에 주간이 얹히면 3N 에 가까워진다. 개인 계정 한도 100명 기준으로 **구독자 35명이 이미 70%를 쓴다.** 매주 월·화 이틀이 위험하고, 구독자가 늘면 평일도 무너진다.

Workspace 계정은 1,500명이다. 이것이 구독자 상한을 푸는 유일한 경로다.

## 2. 무엇만 바꾸는가 — 최소 이전 원칙

**한도는 스크립트를 실행하는 계정을 따른다.** 그래서 옮겨야 하는 것은 *실행 계정* 하나뿐이다. 나머지는 최대한 그대로 둔다 — 건드릴수록 §3 의 것들이 깨진다.

| 대상 | 옮기나 | 이유 |
|---|---|---|
| Apps Script 실행 계정 | **옮긴다** | 한도가 여기 묶여 있다 |
| 스프레드시트 소유권 | **안 옮긴다** | 게시 CSV URL 이 바뀌면 GitHub Secret 7개가 죽는다. 공유(편집자)로 충분하다 |
| `CFG.WEBAPP_URL` | **안 바꾼다** | 기존 발송분의 수신거부 링크가 이 URL 을 담고 있다(§3-②) |
| 도메인·DNS | 새로 설정 | `noreply@brevislab.com` 발신과 SPF·DKIM·DMARC |

## 3. 조용히 깨지는 것 다섯 — 이전의 실제 위험

### ① SALT — 수신거부 토큰의 근거

```javascript
function token_(email) {
  Utilities.computeDigest(SHA_256, email.toLowerCase().trim() + CFG.SALT)
}
```

`SALT` 는 **운영 Apps Script 의 CFG 에만** 있다. 저장소본은 `"bsl-CHANGE-ME-token-salt"` 플레이스홀더다. 새 프로젝트에 옛 SALT 를 넣지 않으면 **지금까지 나간 모든 메일의 수신거부 링크가 무효**가 된다. 에러가 아니라 "해당 구독자 없음"으로 조용히 실패하고, 구독자는 해지할 방법을 잃는다 — 스팸 신고로 이어질 수 있다.

**이전 작업의 첫 단계는 옛 SALT 를 안전하게 복사하는 것이다.** 이걸 못 하면 이전 자체를 시작하지 말 것.

### ② WEBAPP_URL — 이미 발송된 메일 안에 박혀 있다

수신거부 링크 = `CFG.WEBAPP_URL` + 토큰. 과거 메일에는 **옛 배포 URL** 이 들어 있다. 새 프로젝트를 배포하면 URL 이 달라지므로:

- **옛 배포는 살려 둔다.** 트리거만 지우고 웹앱은 그대로 둬서 과거 링크가 계속 동작하게 한다.
- **새 프로젝트의 `CFG.WEBAPP_URL` 도 옛 URL 로 둔다.** 그래야 해지 창구가 하나로 유지된다.

옛 웹앱은 공유된 관심분야 시트에 쓰므로 소유권을 안 옮겨도 동작한다.

### ③ 웹앱 배포 URL → GitHub Secret 2개

파이프라인이 시트에 쓰는 통로다. 새로 배포하면 URL 이 바뀐다.

```
MARKET_WEBAPP_URL    market/Code.gs doPost — 시장-일일·주간-발행항목·주간-딥다이브 append
WEEKLY_MAILER_URL    mailer 트리거 — 주간 발송 연동
```

**바꾸지 않으면 게이트가 옛 웹앱에 쓰고, 새 계정 쪽 시트에는 아무것도 안 들어온다.** 에러 없이 조용하다.

### ④ 게시 CSV URL → GitHub Secret 7개

시트 소유권을 옮기면 게시 URL 이 재발급될 수 있다.

```
DASH_MANUAL_CSV · MARKET_CONFIG_CSV · SETTINGS_CSV · WEEKLY_DEEPDIVE_CSV
WEEKLY_DRAFT_CSV · WEEKLY_RELEASE_CSV · WEEKLY_RELEASE_ITEMS_CSV
```

**그래서 소유권을 옮기지 않는다(§2).** 공유로 충분하다. 부득이 옮긴다면 이 7개를 전부 재발급·갱신하고, `prepare_weekly_release.py` 가 원장을 못 읽으면 fail-closed 로 멈추는 것을 확인할 것.

### ⑤ 트리거 중복 → 이중 발송

옛 프로젝트와 새 프로젝트에 트리거가 동시에 있으면 **구독자가 같은 메일을 두 번 받는다.** 주간·스페셜은 발송로그로 막히지만 **일일은 로그가 없어 그대로 두 번 나간다.**

옮겨야 할 트리거 8개:

```
sendDailyMarket · preflightQuotes · syncDailySchedule
sendWeekly · sendSpecialDue
weeklyAlertDraft · weeklyAlertDeadline · weeklyAlertResult
```

**반드시 옛 트리거를 먼저 지우고 새 트리거를 만든다.** 순서가 바뀌면 겹치는 창이 생긴다.

## 4. 순서

각 단계마다 검증을 통과해야 다음으로 간다.

### 0단계 — 준비 (발송에 영향 없음)

```
□ 옛 Apps Script CFG 에서 SALT 값을 확보한다(§3-①). 확보 못 하면 중단.
□ 옛 배포 URL(CFG.WEBAPP_URL)을 기록한다(§3-②).
□ 현재 트리거 8개와 각 시각을 기록한다 — 새 계정에서 같은 시각으로 재생성해야 한다.
□ 스크립트 속성을 기록한다: WEEKLY_CRON_TOKEN · GH_DISPATCH_TOKEN(QUOTES_TOKEN_PROP)
  · daily_send_time_applied(DAILY_TIME_PROP) · market 웹앱의 TOKEN.
```

### 1단계 — Workspace 계정과 도메인

```
□ Google Workspace 구독(Business Starter, 사용자 1명)
□ brevislab.com 도메인 소유 확인
□ DNS: MX · SPF · DKIM · DMARC
□ 검증: 새 계정에서 외부 주소로 테스트 메일 1통 → 수신측 헤더에서 SPF/DKIM pass 확인
        (Gmail 이면 '원본 보기' 에서 SPF·DKIM·DMARC 가 전부 PASS 인지)
```

⚠️ DMARC 는 처음에 `p=none` 으로 두고 며칠 리포트를 본 뒤 조인다. 바로 `p=reject` 로 두면 설정 실수가 곧 전량 반송이다.

### 2단계 — 시트 공유 (소유권 이전 아님)

```
□ BSL_market · 응답 시트 · 관심분야(기술/금융/경제) 를 새 계정에 편집자로 공유
□ 검증: 새 계정에서 SpreadsheetApp.openById 로 각 시트를 읽을 수 있는지
```

### 3단계 — Apps Script 복제

```
□ mailer / market / admin 프로젝트를 새 계정으로 복사
□ CFG 를 손으로 채운다 — 전체 붙여넣기 금지(SALT·TEST_MODE·MARKET_SHEET_ID 가 플레이스홀더)
  · SALT       = 0단계에서 확보한 옛 값 (§3-①)
  · WEBAPP_URL = 옛 배포 URL 그대로     (§3-②)
□ 스크립트 속성 재설정(0단계 기록분)
□ 편집기에서 아무 함수나 실행해 권한 승인 창을 통과시킨다
  ⚠️ MailApp 과 GmailApp 은 스코프가 다르다. 웹앱은 재배포로 새 권한을 받지만
     시간 트리거는 사람이 재승인해야 한다 — 2026-08-17 에 이걸 놓쳐 발송이 전면 중단됐다.
□ 검증: TEST_MODE = true 로 sendWeekly 미리보기 → 운영자에게만 도착
```

### 4단계 — 전환 (되돌리기 어려운 지점)

**하루 중 발송이 없는 시간대에 한다.** 일일 07:20 · 주간 월 09:00 · 스페셜 15분 폴링을 모두 피할 것 — 평일 오후가 무난하다.

```
□ 옛 프로젝트의 트리거 8개를 전부 삭제 (§3-⑤)
□ 옛 프로젝트의 웹앱 배포는 그대로 둔다 — 과거 수신거부 링크가 여기로 온다 (§3-②)
□ 새 프로젝트에서 웹앱 배포 → 새 URL 두 개를 기록
□ GitHub Secret 갱신: MARKET_WEBAPP_URL · WEEKLY_MAILER_URL (§3-③)
□ 새 프로젝트에 트리거 8개 생성 (0단계에 기록한 같은 시각)
□ TEST_MODE = false
```

### 5단계 — 검증

```
□ MailApp.getRemainingDailyQuota() 가 1,000 이상을 반환하는지 (개인 계정이면 100 근처)
□ 다음 일일 시황(07:20)이 실제로 발송되는지 — 로그에 [일일] ... 발송 N
□ 받은 메일의 발신자가 noreply@brevislab.com 인지, 헤더에서 SPF/DKIM PASS 인지
□ 그 메일의 수신거부 링크를 눌러 실제로 해지되는지 (§3-① SALT 검증)
□ 과거 메일 하나를 찾아 그 수신거부 링크도 여전히 동작하는지 (§3-② 검증)
□ 게이트가 새 웹앱에 쓰는지 — 다음 월요일 04:00 후 주간-발행항목에 행이 들어오는지 (§3-③)
□ 구독자가 같은 메일을 두 번 받지 않았는지 (§3-⑤)
```

이전이 끝난 뒤에 적용한다. 계정이 준비되기 전에 넣으면 개인 계정에서 잘못된 발신자로 나간다.

```
□ mailer/Code.gs sendMail_  — options.from 또는 CFG.SENDER 를 noreply@brevislab.com 으로
  (Workspace 별칭 설정 여부에 따라 방식이 갈린다. 실제 계정에서 확인 후 결정)
□ mailQuotaOk_ / mailQuotaWarn_ 의 안내 문구에서 '100명 → 1,500명' 반영
□ CLAUDE.md 의 '구독자 50명 상한' 서술 갱신
```

## 6. 롤백

4단계까지는 되돌릴 수 있다. 옛 프로젝트를 지우지 않았기 때문이다.

```
□ 새 프로젝트의 트리거 8개 삭제
□ 옛 프로젝트의 트리거 8개 재생성(0단계 기록분)
□ GitHub Secret 두 개를 옛 URL 로 되돌림
```

**옛 프로젝트와 옛 배포는 최소 한 달 지우지 않는다.** 과거 수신거부 링크가 거기로 오고, 롤백 경로이기도 하다.

## 7. 확인이 필요한 미지수

아래는 문서 작성 시점에 검증하지 못했다. **추정으로 진행하지 말고 실제로 확인할 것.**

- 개인 계정 → Workspace 계정으로 **Apps Script 프로젝트 소유권 이전**이 가능한가. 가능하다면 배포 URL 이 유지될 수 있고, 그러면 §3-②·③ 이 통째로 사라진다. 복제보다 훨씬 안전하므로 **먼저 시도해 볼 가치가 있다.**
- Workspace 별칭(`noreply@`)으로 `GmailApp.sendEmail` 발신이 되는지, 아니면 별도 설정이 필요한지.
- Workspace 한도 1,500 이 이 사용 형태(스크립트 발송)에 그대로 적용되는지.

## 8. 이전까지의 임시 안전망 (2026-09-01 적용, 커밋 3522a8e)

이전이 끝날 때까지 지금 구조로 돌아야 한다. 그 기간의 방어는 이렇게 돼 있다.

| | 발송로그 | 한도 부족 시 |
|---|---|---|
| 일일 | 없음 | **막고** 운영자에게 알림 (`mailQuotaOk_`) |
| 주간·스페셜 | 있음 | 막지 않고 **알림** (`mailQuotaWarn_`) — 끊겨도 못 받은 사람에게만 다시 나감 |

⚠️ 이 커밋은 **Apps Script 수동 배포가 필요하다.** `mailQuotaWarn_`(신규) · `mailQuotaOk_` · `sendWeeklyUnlocked_` · `specialSendRow_` 네 함수를 함수 단위로 붙여넣을 것. 아직 안 했다면 이전 전에 먼저 한다 — 안 하면 이전 기간에 주간이 무방비다.
